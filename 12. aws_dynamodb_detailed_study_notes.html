AWS DynamoDB — Detailed & Structured Notes

1. What is Amazon DynamoDB?

Amazon DynamoDB is a fully managed NoSQL database service provided by AWS.

In the previous section, we studied Amazon RDS, which is mainly used for relational data.
DynamoDB is different because it is a NoSQL database designed for flexible, non-tabular data and highly scalable applications.

RDS vs DynamoDB

RDS DynamoDB
Relational database NoSQL database
Structured/tabular data Flexible, non-tabular data
Uses rows and columns Uses items and attributes
SQL-based NoSQL API-based
Schema is generally more structured Flexible schema
Example: MySQL, PostgreSQL DynamoDB

2. What is NoSQL?

NoSQL = Not Only SQL

NoSQL databases are generally designed for data that does not need to follow a rigid table structure.
A common representation is similar to JSON.

Example

{ "name": "Raju", "email": "raju@example.com", "age": 30 }

Here:
name → key/attribute  |  Raju → value
email → key/attribute  |  raju@... → value
age → key/attribute  |  30 → value
This entire object can be treated as a document/item.

Important Point

Different items in DynamoDB do not necessarily need to contain exactly the same attributes.

For example:

Item 1:
ID = 01
Username = Raju

Item 2:
ID = 02
Username = Shyam
Age = 30

The second item contains Age, while the first item does not. This demonstrates DynamoDB's flexible schema.

3. Basic DynamoDB Terminology

The most important terms are:

Table: A table is a collection where DynamoDB stores items. Example: Contacts

Item: An item is an individual record inside a DynamoDB table. Example: {"id": "01", "username": "Raju"}

Attribute: An attribute is a piece of information inside an item. Example: id, username, age, email

Simple Structure

DynamoDB │ └── Table │ ├── Item 1 │ ├── id │ └── username │ ├── Item 2 │ ├── id │ ├── username │ └── age │ └── Item 3 ├── id └── email

7. Partition Key

When creating the table, a partition key needs to be defined. Example:

Partition Key: id
Type: String

What is a Partition Key?

The partition key is used to uniquely identify items and determine how DynamoDB distributes data internally. For the simple example: id = 01, id = 02, id = 03. Each item can be identified using its key.

SQL Comparison

Conceptually, the partition key can be compared with the role of a primary key in a relational database, although DynamoDB's key design and data distribution work differently.

8. Creating Items Manually

After creating the table:

Contacts↓Explore Table Items↓Create Item

Initially, the table contains no data. Example item:

id = 01
username = Raju

Another item:

id = 02
username = Shyam

You can also add different attributes: id = 02, username = Shyam, age = 30. The important concept is that the items can have different attributes.

9. Flexible Data Model

This is one of DynamoDB's major characteristics. Consider:

Item 1

{ "id": "01", "username": "Raju" }

Item 2

{ "id": "02", "username": "Shyam", "age": 30 }

The two items don't have exactly the same set of attributes. This is different from a traditional relational table where columns are normally defined as part of the table schema.

Key Concept DynamoDB provides a flexible schema at the item/attribute level. However, the key schema still matters and must be designed properly.

10. Why DynamoDB is Serverless

DynamoDB is a fully managed serverless database service.

With a traditional database server, you may need to think about: Server instances, CPU, Memory, Storage, Operating system, Patching, Database infrastructure.

With DynamoDB, AWS manages the underlying infrastructure. You don't need to manually provision a database server in the same way as a traditional database deployment.

Simple Comparison

Traditional Database

Server↓CPU↓Memory↓Storage↓Database

DynamoDB

Application↓DynamoDB↓AWS-managed infrastructure

11. Automatic Scaling  |  12. Zero-Server Management

11. Automatic Scaling: DynamoDB is designed to handle changing workloads. Suppose your application normally receives 100 requests but suddenly receives 10,000 requests. DynamoDB can scale according to the selected capacity mode and workload.

Scaling Concept:

Low Traffic→Lower Capacity
Traffic increases→More Capacity
Traffic decreases→Capacity decreases

This is especially useful for fluctuating workloads.

12. Zero-Server Management: One major advantage is that you don't have to manage database servers yourself. You don't need to manually manage:

  • Database server provisioning
  • Operating system maintenance
  • Hardware
  • Database infrastructure scaling

AWS manages the underlying service infrastructure.

13. Provisioned Capacity vs 14. On-Demand Capacity

DynamoDB provides different capacity approaches.

A. Provisioned Capacity

You specify the expected capacity. For example:

Read Capacity:
Minimum → X | Maximum → Y

Write Capacity:
Minimum → X | Maximum → Y

You can configure auto scaling so capacity can increase or decrease according to demand. Concept: Low traffic → Lower provisioned capacity. High traffic → Higher provisioned capacity. This can be useful when workload patterns are relatively predictable.

B. On-Demand Capacity

With on-demand capacity, you don't have to manage a fixed provisioned capacity in the same way. The service is designed to handle requests automatically and billing is based on request usage.

Best suited for:

  • Unpredictable traffic
  • New applications
  • Spiky workloads
  • Applications where traffic patterns are difficult to estimate

Example: Normal traffic → Low request activity. Sudden traffic spike → Higher request activity. Traffic falls → Lower activity.

15. Read Capacity and Write Capacity

Two important concepts are:

Read Capacity: Represents capacity for read operations.
Write Capacity: Represents capacity for write operations.

Application │ ├── Read Request │ ↓ │ Read Capacity │ └── Write Request ↓ Write Capacity

These concepts are particularly relevant when using provisioned capacity.

16. Auto Scaling

DynamoDB can use auto scaling with provisioned capacity. You can configure: Minimum capacity, Maximum capacity, Target utilization.

For example: Minimum Capacity → 1  |  Maximum Capacity → 10  |  Target Utilization → 70%

These values are only examples from the practical concept; actual settings should be chosen according to the application's workload.

Auto Scaling Flow:

Traffic decreases→Capacity decreases→Lower resource usage
Traffic increases→Capacity increases→More requests can be handled

17. Maximum Table Throughput

The course also demonstrates configuring maximum read/write throughput. The exact limits depend on the DynamoDB configuration and current AWS service limits.

Concept You can control and monitor the capacity available to your DynamoDB workload.

18. Monitoring Auto Scaling

DynamoDB provides monitoring information about capacity and scaling activity. You can inspect:

  • Current capacity
  • Read activity
  • Write activity
  • Scaling changes
  • Table metrics

This allows you to understand how the database is responding to application traffic.

19. DynamoDB Indexes

Indexes are used to improve the efficiency of queries based on attributes other than the primary key. Suppose your application frequently searches using: username. You can create an appropriate index so that queries based on that attribute can be handled efficiently.

Concept

Without suitable indexing:

Query→Find matching data

With an appropriate index:

Query→Index→Matching items
Important

DynamoDB has concepts such as:

  • Primary key
  • Local Secondary Index (LSI)
  • Global Secondary Index (GSI)

Index design should be based on the application's access patterns.

20. Backup and Point-in-Time Recovery

Backup is extremely important for databases. DynamoDB supports backup and recovery capabilities.

Point-in-Time Recovery (PITR)

Point-in-Time Recovery allows you to restore table data to a point in time within the supported recovery window.

Example: Suppose:

  • 10:00 → Database is correct
  • 10:30 → Data accidentally changed
  • 11:00 → Problem discovered

With appropriate point-in-time recovery configuration, you can recover the table to an earlier point in time.

Concept

Past │ ├── 10:00 ├── 10:15 ├── 10:30 ├── 10:45 └── 11:00 ↓ Choose recovery point

This is useful for accidental changes or deletions.

21. On-Demand Backups

You can also create an on-demand backup. This can be useful when you want to explicitly preserve a table's data before performing an important operation.

DynamoDB Table │ ├── Point-in-Time Recovery │ └── On-Demand Backup

22. Delete Protection

DynamoDB provides deletion protection. When enabled, it helps protect a table from accidental deletion.

Without protection: Accidental delete → Table deleted → Data loss
With protection: Delete attempt → Protection enabled → Additional protection against deletion

Useful for important production tables.

23. Time to Live (TTL)

DynamoDB supports Time to Live (TTL). TTL allows expired items to be automatically removed after a specified expiration time.

Example

Suppose you store temporary data:

{ "id": "101", "session": "ABC", "expiresAt": 1750000000 }

Once the item reaches its expiration condition, DynamoDB can automatically remove it.

Useful for:

  • Temporary data / Sessions
  • Cache-like information
  • Expiring records / Temp state

24. Encryption

DynamoDB supports encryption of data at rest. Encryption helps protect stored database data. For production systems, encryption should be part of the overall security design.

Important Security Note

Do not hard-code or expose access keys in application commands, source code, screenshots, or public repositories. For an EC2 application, the preferred approach is usually: EC2 → IAM Role → DynamoDB permissions. This avoids manually managing long-lived access keys.

Instead of giving an EC2 instance permanent access keys, attach an IAM role.

EC2 │ ▼ IAM Role │ ▼ DynamoDB Permissions │ ▼ DynamoDB

33. Creating an IAM Role: IAM → Roles → Create Role → AWS Service → EC2. Then permissions are assigned. Principle of Least Privilege: Instead of "DynamoDB Full Access", prefer only what's needed (GetItem, PutItem, UpdateItem, DeleteItem, Query).

39. Global Tables

DynamoDB Global Tables allow a table to be replicated across multiple AWS Regions. This is useful for globally distributed applications (e.g. users in USA, Europe, Asia).

Global Application │ ┌───────────────┼───────────────┐ ↓ ↓ ↓ USA Region Europe Region Asia Region │ │ │ └───────────────┼───────────────┘ Global Table

Helps provide: Multi-Region availability, Lower latency, Disaster recovery, Global app support.

40. DAX & 41. Caching

DynamoDB Accelerator (DAX) is a fully managed, in-memory cache designed specifically for DynamoDB. It is used when applications require extremely fast access to frequently requested data.

Normal vs DAX Flow:

App→DynamoDB
App→DAX→DynamoDB

41. Caching: If app repeatedly requests "Product A", DAX returns cached result instead of hitting DynamoDB every time, reducing latency and DB reads.

48. DynamoDB Use Cases  |  49. Key Advantages

48. Use Cases

DynamoDB is particularly useful for workloads such as:

  1. Web Applications: High-traffic web apps requiring scalable data storage.
  2. Mobile Applications: Large numbers of users and requests.
  3. Gaming: Fast reads/writes, high scalability, large concurrent users.
  4. IoT: Generating huge numbers of events and records.
  5. Advertising Technology: Extremely high request rates and low latency.
  6. Real-Time Applications: Where fast data access is important.

49. Key Advantages

  • Fully Managed & Serverless: AWS manages infra; no servers to manage directly.
  • Automatic Scaling: Designed to handle changing traffic.
  • Flexible Data Model: Items can contain different attributes.
  • High Performance: Designed for low-latency DB operations.
  • High Availability: Managed infra for HA.
  • Backup & Recovery: Backup and PITR capabilities.
  • Global Tables: Multi-Region architectures.
  • DAX: In-memory caching option.

50. Important Security Best Practices  |  51. Cleanup

When implementing DynamoDB:

  • 1. Prefer IAM Roles: For EC2: EC2 → IAM Role → DynamoDB. Avoid long-lived access keys in code.
  • 2. Use Least Privilege: Give only needed permissions.
  • 3. Protect Credentials: Never expose AWS Access Key or Secret Access Key in GitHub, Docker images, code, or screenshots.
  • 4. Enable Encryption: Use appropriate AWS encryption.
  • 5. Enable Recovery Features: Backup and PITR for prod.
  • 6. Enable Delete Protection: Protect critical tables.

DynamoDB Table → Delete EC2 Instance → Terminate IAM Access Keys → Deactivate/Delete

Always check AWS Billing / Cost Management after practicals.

53. Interview Questions

Q1. What is DynamoDB?
A fully managed, serverless NoSQL database service provided by AWS, designed for highly scalable and low-latency applications.
Q2. Difference between RDS and DynamoDB?
RDS is a managed relational database service, while DynamoDB is a managed NoSQL database service.
Q3. What is an item?
An individual record stored inside a DynamoDB table.
Q4. What is an attribute?
A property or piece of data belonging to an item.
Q5. What is a partition key?
A key attribute used to identify items and determine how DynamoDB distributes data.
Q6. Is DynamoDB serverless?
Yes. Fully managed serverless database service; users don't provision or manage servers directly.
Q7. What is auto scaling?
Adjusts provisioned read/write capacity according to workload demand.
Q8. What is on-demand capacity?
Handles request traffic without requiring a fixed provisioned capacity, billing based on request usage.
Q9. What is DAX?
DynamoDB Accelerator, a fully managed in-memory caching service specifically for DynamoDB.
Q10. What are Global Tables?
Allow DynamoDB data to be replicated across multiple AWS Regions for globally distributed apps.
Q11. What is Point-in-Time Recovery?
PITR allows a table to be restored to a selected point in time within the supported recovery period.
Q12. What is TTL?
Time to Live automatically expires items based on an expiration attribute.
