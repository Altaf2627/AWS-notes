⚙️ NGINX — Detailed & Structured Notes

1. What is NGINX?

NGINX (pronounced "Engine-X") is a web server used to serve and deliver web content to users.

However, it is not limited to being just a web server. It can also work as a:

  • Reverse Proxy
  • Load Balancer
  • Caching Server
  • HTTP/HTTPS Server
  • TCP/UDP Proxy (with stream config)
⭐ Key Point

NGINX = Web Server + Reverse Proxy + Load Balancer + Caching + More

2. What is a Web Server?

A web server is software that receives requests from clients (usually web browsers) and sends back web content.

Basic Flow

User / Browser ↓ Internet ↓ Web Server ↓ Website Files (HTML/CSS/JS) ↓ Response ↓ User / Browser

3. Why Do We Need NGINX?

If you create index.html and style.css, how does a user access them? NGINX receives the HTTP request and returns the requested files based on its configuration.

4. Practical Setup  |  5. Launching an EC2 Instance

To practice, you need a server. An AWS EC2 instance is perfect.

  • Step 1: Give instance a name (e.g., nginx-server)
  • Step 2: Select OS (Amazon Linux)
  • Step 3: Configure Key Pair for SSH

Step 4: Network Access

AWS Security Groups act as a virtual firewall. To view an HTTP site, you MUST allow TCP Port 80.

13. NGINX Configuration  |  14. Structure

The main NGINX config file is typically located at: /etc/nginx/nginx.conf

The configuration is organized into hierarchical blocks:

events { ... } http { server { location / { ... } } }

Blocks Breakdown (15 - 18)

15. events

Handles connection processing. Can be empty for basic setups: events {}. (Make sure it's plural!)

16. http

Contains all HTTP traffic configs: server blocks, logging, MIME types.

17. server

Defines how to handle requests for a specific virtual server/site. Contains listen, server_name, etc.

18. location

Determines how requests for specific URI paths (e.g., / or /about/) are processed.

19. listen  |  20. root

listen 80;
Tells NGINX to listen for HTTP traffic on port 80. You can change this to 8080 or 443.

root /usr/share/nginx/html;
Tells NGINX the physical directory on the server where the website files are stored.

22. Creating Your Own Website

Before editing nginx.conf, always create a backup!

sudo cp /etc/nginx/nginx.conf /etc/nginx/nginx.conf.backup

23. Minimal NGINX Configuration

events {} http { server { listen 80; root /usr/share/nginx/html; index index.html; } }

24. Testing Config  |  25. Reloading

⭐ The Golden Rule

Edit Config → sudo nginx -t → If OK → sudo systemctl reload nginx

Never blindly reload. Always test syntax with nginx -t. Reloading applies changes gracefully without dropping active connections.

Changing Ports & Security Groups (29 - 31)

If you change listen 80; to listen 8080;, your website won't work immediately. Why?

Two Layers to Allow

  1. NGINX: Must listen on 8080.
  2. AWS Security Group: Must allow inbound TCP 8080 from the internet.
Internet ↓ AWS Security Group (Allows 8080?) ↓ NGINX Server (Listening on 8080?)

32 - 35. NGINX Logging

Logs are stored under /var/log/nginx/. They are critical for troubleshooting.

Log FilePurpose
access.log Records all incoming client requests (IP, time, URI, status).
error.log Records internal errors, warnings, and missing files.
Memory Trick ACCESS → Who requested what?  |  ERROR → What went wrong?

36. Hosting Multiple Websites  |  37. server_name

NGINX uses multiple server blocks and the server_name directive to host multiple websites on one server.

server { listen 80; server_name example.com; root /usr/share/nginx/html/example.com; } server { listen 80; server_name myapp.com; root /usr/share/nginx/html/myapp.com; }

DNS vs server_name

DNS routes both example.com and myapp.com to your EC2 IP.

NGINX looks at the HTTP Host header and uses server_name to pick the right block!

38 & 39. MIME Types

Browsers need to know file types to render them correctly (e.g., HTML vs CSS vs JS). You must include MIME types in your config:

include /etc/nginx/mime.types;
default_type application/octet-stream;

Without this, your CSS files might load as plain text, breaking your site's styling!

44. Custom 404 Page  |  45. try_files

Custom 404 Page

error_page 404 /404.html;

Returns a friendly HTML page instead of NGINX's default "Not Found" error.

try_files Directive

try_files $uri $uri/ =404;

Instructs NGINX to: Check for file → Check for directory → Return 404 if neither exists.

HTTPS and SSL/TLS (47 - 49)

HTTPS (HTTP over TLS) encrypts data between the client and the server, protecting sensitive information like passwords.

  • SSL vs TLS: TLS (Transport Layer Security) is the modern, secure protocol. SSL is obsolete, though people still say "SSL certificate."
Browser → HTTPS :443 → NGINX (TLS decrypts) → App

50 - 53. Let's Encrypt & Certbot

Let's Encrypt is a free, automated Certificate Authority. Certbot is the tool used to fetch and renew these certs.

sudo certbot certonly --standalone -d example.com

⚠️ Standalone mode requires Port 80 to be free, meaning NGINX must temporarily be stopped.

Certificate Files

Stored in /etc/letsencrypt/live/...

  • fullchain.pem: The public cert.
  • privkey.pem: The private key. Never expose this!

54. NGINX HTTPS Config  |  56. HTTP → HTTPS Redirect

# Redirect HTTP to HTTPS server { listen 80; server_name example.com; return 301 https://$host$request_uri; } # Secure HTTPS Server server { listen 443 ssl; server_name example.com; ssl_certificate /etc/letsencrypt/.../fullchain.pem; ssl_certificate_key /etc/letsencrypt/.../privkey.pem; root /usr/share/nginx/html/example.com; }

57 - 59. Reverse Proxy & Benefits

Instead of the client directly contacting a backend server (Node.js, Tomcat, etc.), NGINX sits in front of it.

Client → NGINX (Reverse Proxy) → Backend Server

Key Benefits

  • Security: Backend stays private
  • Load Balancing: Distribute traffic
  • Caching: Store responses
  • Centralized HTTPS: Terminate TLS once

61. proxy_pass & Headers  |  63. Security

location / { proxy_pass http://10.0.1.10:80; proxy_set_header Host $host; proxy_set_header X-Real-IP $remote_addr; }

proxy_pass tells NGINX where to forward traffic. Headers like X-Real-IP help the backend know the original client's IP, instead of just seeing NGINX's IP.

63. Reverse Proxy Security

Never leave your backend server open to the public internet (0.0.0.0/0). Restrict its AWS Security Group to only accept traffic from the NGINX server's private IP/SG.

64. Load Balancing  |  66. upstream Block

When traffic grows, one backend server isn't enough. NGINX can distribute traffic among a group of servers using the upstream block.

upstream backend_pool { server 10.0.1.10:80; server 10.0.1.11:80; } server { location / { proxy_pass http://backend_pool; } }
Clients ↓ NGINX ↓ backend_pool / \ ↓ ↓ Web 1 Web 2

Load Balancing Algorithms & Failover (67 - 71)

Algorithm / FeatureHow it works
Round Robin (Default) Takes turns evenly. (Req1→Srv1, Req2→Srv2, Req3→Srv1)
Least Connections Sends new request to the server with the fewest active connections. Great for varying request durations.
Weighted weight=3; Higher weight = gets more traffic proportionally. Best when servers have unequal CPU/RAM.
Backup / Failover backup; Only receives traffic if the primary servers are down/unavailable. High Availability redundancy!

72 - 76. Timeouts

Tune timeouts based on your application's workload to prevent hanging connections or premature disconnects.

  • keepalive_timeout: Max idle time for a keep-alive connection.
  • proxy_connect_timeout: Max time to establish connection to backend.
  • proxy_read_timeout: Max time waiting for backend response.
  • proxy_send_timeout: Max time to send data to backend.

77 - 80. Caching

Caching stores copies of responses at the NGINX layer so future identical requests don't hit the backend. This provides faster responses and reduced backend load.

Request 1: Client → NGINX → Backend → Response → Cache at NGINX → Client Request 2: Client → NGINX Cache → Client (Backend completely skipped!)

Basic Cache Config

proxy_cache_path /var/cache/nginx keys_zone=my_cache:10m max_size=1g inactive=60m; server { location / { proxy_cache my_cache; proxy_pass http://backend; } }

⚠️ Warning

Do NOT cache everything blindly! Do not cache sensitive user data (like logged-in profiles or checkout pages). Incorrect caching serves the wrong data to the wrong user.

87. Troubleshooting Checklist

Site Doesn't Load?

  • Check systemctl status nginx
  • Test config nginx -t
  • AWS Security Group allows 80/443?
  • EC2 Public IP correct?

404 Error?

  • Check root path and index
  • Check try_files config
  • File permissions

CSS Not Loading?

Check include /etc/nginx/mime.types;. Hard refresh browser (Ctrl+Shift+R).

88. Best Practices

  • Always run sudo nginx -t before reloading!
  • Keep backups of nginx.conf before editing.
  • Use HTTPS for production. Protect privkey.pem.
  • Monitor access.log and error.log.
  • Keep backend servers private (only accessible by NGINX).
