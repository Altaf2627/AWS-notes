☁️ Amazon CloudFront — Content Delivery Network (CDN)

1. Introduction

In the previous section, we worked with:

  • Amazon EC2 — to host a website/application
  • Amazon S3 — to store website files and static content
  • Amazon Route 53 — for DNS and routing

Now we take the concept one level further.

🎯 The Next Challenge

Suppose your website is hosted in the Mumbai AWS Region.
If users from Europe access the website, their requests may need to travel a long distance to reach the Mumbai Region.

This can result in:

  • Higher latency
  • Longer loading time
  • Slower content delivery
  • Poorer user experience

Therefore, the next challenge is: How can we serve our website globally with low latency and better performance?

2. Two Approaches to Global Website Delivery

Suppose we want users around the world to access our website quickly.

Approach 1: Deploy Multiple EC2 Instances

We could deploy: One EC2 instance in Mumbai, another EC2 instance in Stockholm/Europe, and more instances in other regions. Then users could be served from a geographically closer region.

Users ┌──────┴──────┐ ↓ ↓ Europe India ↓ ↓ Stockholm Mumbai EC2 EC2

❌ Problem

The more EC2 instances and AWS Regions we use:

  • The more resources we have to manage
  • The higher the infrastructure cost
  • The more complex the architecture becomes

Therefore, we need a more efficient solution.

3. ⭐ Solution: Amazon CloudFront

The solution is: Amazon CloudFront

Amazon CloudFront is a Content Delivery Network (CDN) provided by AWS.

Main Purpose

CloudFront helps: Deliver website content to users with lower latency and better performance.

Instead of every user directly accessing the original server, CloudFront can cache content at locations that are geographically closer to users.

4. What is a CDN?

CDN = Content Delivery Network

A CDN is a globally distributed network used to deliver content efficiently to users. Instead of serving every request from one central server, a CDN stores/caches frequently requested content at geographically distributed locations.

Without CDN:

User in Europe↓Internet↓Mumbai AWS Region↓S3/EC2

With CloudFront:

User in Europe↓Nearest CloudFront Edge Location↓Cached Content

This can significantly reduce the distance between the user and the content being served.

5. How CloudFront Works

CloudFront works using caching. Suppose your website contains: HTML, CSS, JavaScript, Images, Videos, Other static files. CloudFront can cache suitable content at its distributed locations.

First Request

Suppose a user in Europe requests your website for the first time.

European User↓CloudFront Edge Location↓Cache Miss↓Origin (S3/EC2)↓Content returned↓Edge Location caches content↓User

The first request may need to go back to the origin.

6. Subsequent Requests

Now another user near the same CloudFront location requests the same cached content.

Second User↓CloudFront Edge Location↓Cache Hit↓Content delivered directly

The request does not necessarily need to go all the way back to the original S3 bucket or EC2 server.

⭐ Result

Lower latency | Faster content delivery | Better user experience | Reduced load on the origin

7. Origin

The origin is the original location from which CloudFront retrieves content. CloudFront can work with different types of origins.

Examples mentioned in the practical: Amazon S3, Elastic Load Balancer, API Gateway, Other supported origins.

CloudFront ↓ Origin ┌───────┼────────┐ ↓ ↓ ↓ S3 EC2 ELB

8. What Does CloudFront Cache?  |  9. Dynamic Content

Static Content

CloudFront can cache content such as: Images, CSS files, JavaScript files, HTML, Videos, Other static website assets.

For example, instead of repeatedly downloading high-resolution images from the origin, CloudFront caches them closer to users.

9. Dynamic Content

CloudFront can cache certain dynamic content (HTML/API responses). However, sensitive, user-specific data and backend logic are generally not cached by default.

⚠️ Important

Avoid caching data that is: User-specific, Sensitive, Private, or Frequently changing in a way that could cause incorrect data to be served.

10. CloudFront Edge Locations

One of the most important CloudFront concepts is: Edge Location.

An Edge Location is a CloudFront location where content can be cached and served closer to users.

Example: Suppose users are located in India, Europe, North America, and Asia-Pacific. CloudFront has a globally distributed network of locations. Therefore, users can potentially receive content from a location closer to them.

11. Why Edge Locations Matter

Imagine your origin is located in Mumbai.

Without CloudFront:

User→Mumbai Origin

With CloudFront:

User→Nearest Edge Location→Cached Content

The physical/network distance can be reduced, improving delivery performance.

12. CloudFront vs Multiple EC2 Instances

This is an important architectural comparison.

Multiple EC2 Instances CloudFront
Deploy servers in multiple regions Distribute/cache content globally
More infrastructure Less need for multiple origin servers for cached content
Higher management complexity Managed CDN service
Can increase infrastructure cost Cost primarily depends on usage and configuration
Useful for globally distributed application compute Excellent for content delivery and caching
⭐ Important CloudFront does not simply replace multiple regional application servers in every situation. The correct solution depends on the application's architecture and requirements.

13. Practical — Website Deployment  |  14 & 15

The practical example uses a simple website containing index.html, images, etc. The website is first uploaded to an S3 bucket (e.g. my-website-312024).

14. Why Not Direct S3 Access?

The purpose is to make CloudFront the delivery layer. We want User → CloudFront → S3 instead of User → S3 directly.

15. Create a Distribution

A distribution defines how CloudFront should deliver content.

Origin Domain:

Choose the origin from which CloudFront will retrieve content. For this practical: Amazon S3 Bucket.

CloudFront Configuration (16 - 19)

16. Origin Access

CloudFront needs permission to access the S3 origin. The practical uses the recommended config, allowing CloudFront → S3 while users access content via CloudFront.

17. Cache Policy

Controls caching behavior: What can be cached, how requests are handled, how long content remains cached, and which request characteristics affect caching.

18. Price Class

Controls which CloudFront edge locations are used.

  • All Edge Locations: Broadest global coverage, best performance.
  • Selected regions: Potentially lower cost, restricted usage.

19. Default Root Object

Specifies which object is served when the root of the distribution is requested. For a website, we commonly specify: index.html

20. Create the Distribution  |  21. Domain Name

⚠️ Important CloudFront is a global service, so it is not treated like a normal Region-specific resource. The distribution may take some time to become fully deployed.

Once the distribution is created, CloudFront provides a domain name similar to: xxxxxxxxxxxx.cloudfront.net. This becomes the URL through which users can access the distribution.

User→CloudFront Domain Name→Edge Location→S3 Origin

22. Testing the Website  |  23. Performance Test

Open the CloudFront distribution domain name in a browser. The website should load through CloudFront.

First Request

May take longer because CloudFront may need to retrieve content from the origin (e.g. ~640 ms).

Subsequent Requests

After content is cached, subsequent requests may be faster (e.g. ~200 ms or ~195 ms).

Note Actual performance depends on user location, edge location, network conditions, object size, cache status, and origin performance.

24. Cache Hit and Cache Miss

These two terms are extremely important.

Cache Hit

A requested object is already available in the CloudFront cache.

User↓Edge Location↓Object found↓CACHE HIT↓Content delivered

Result: Usually faster delivery.

Cache Miss

The requested object is not currently available in the cache.

User↓Edge Location↓Object not found↓CACHE MISS↓Origin → Content

25. CloudFront Monitoring  |  Cache Hit Ratio

CloudFront provides monitoring and statistics: Requests, Cache hits, Cache misses, Errors, Traffic.

Cache Hit Ratio: Represents how often requests can be served from cache instead of going to the origin. Generally: Higher cache hit ratio → less work for the origin and potentially faster content delivery.

26. CloudFront Architecture

The complete architecture can be visualized as:

GLOBAL USERS ┌─────────┼─────────┐ ↓ ↓ ↓ Europe India America │ │ │ └─────────┼─────────┘ ↓ CloudFront Edge Locations ↓ Cache / Delivery ↓ Origin ┌─────┴─────┐ ↓ ↓ S3 EC2

The key idea: Users are served through CloudFront, while CloudFront retrieves content from the origin when necessary.

27 & 28. CloudFront Terminology  |  POPs

27.1 Edge Location

A location in the CloudFront network used to serve content closer to users.

27.2 Regional Edge Cache

A larger intermediate caching layer. It can help reduce repeated trips to the origin when content is not available at a particular edge location.

User→Edge Location→Regional Cache→Origin

27.3 Point of Presence (POP)

A network location used to provide connectivity and content delivery services.

28. Embedded POPs

Can involve infrastructure associated with Internet Service Providers (ISPs) to improve network proximity/performance.

29. Browser Cache vs CloudFront Cache

Browser Cache

A browser can cache website content locally for an individual user.

Limitation:

The cache is generally associated with that user's browser. If User B accesses the website, they still need to retrieve content.

CloudFront Cache

CloudFront provides a shared, distributed caching layer.

User A ─┐ ├──→ CloudFront Edge Cache User B ─┤ │ User C ─┘

Allows cached content to be reused for multiple users.

30. CloudFront Pricing Concept

CloudFront pricing is primarily usage-based. The practical highlights that the edge locations themselves are not something you separately pay for simply because they exist.

Costs can depend on: Data transfer, Number of requests, Region/geography, Features used, Configuration. AWS also provides a CloudFront free-tier allowance (verify current pricing).

31. CloudFront vs Multi-Region Hosting

A common question is: Should I use CloudFront or deploy my application in multiple AWS Regions? There is no single answer. It depends on the use case.

Use CloudFront when:

  • You need global content delivery
  • Website contains lots of static assets
  • You want caching
  • You want lower content-delivery latency
  • You want to reduce repeated requests to the origin

Multi-Region Architecture when:

  • Application compute must exist close to users
  • You need regional application redundancy
  • You need active-active or active-passive regional architectures
  • The application itself requires region-level distribution
⭐ Best Concept CloudFront and multi-region architecture are not necessarily alternatives. They can be used together!
Users ↓ CloudFront / \ ↓ ↓ Region 1 Region 2 ↓ ↓ Application Application

32. Request Flow  |  33. CloudFront Cleanup

First Request Flow

User requests website → Request reaches CloudFront → CloudFront checks edge cache → Object not found → Cache Miss → CloudFront requests object from origin → Origin returns object → CloudFront caches content → Delivered to user.

Next Request

User requests same content → CloudFront checks edge cache → Object found → Cache Hit → Delivered directly.

35. ⭐ Key Benefits of CloudFront

  • 1. Low Latency: Delivered from locations closer to users.
  • 2. Faster Website: Cached content without hitting origin.
  • 3. Global Delivery: Distributed delivery network.
  • 4. Better UX: Faster loading improves experience.
  • 5. Reduced Origin Load: Cached requests save origin compute.
  • 6. Scalability: Efficiently handle large numbers of requests.

36. ⚠️ Important Practical Points

  • • CloudFront is a global AWS service.
  • • Original source is called the Origin (e.g. S3).
  • • EC2/app infra can also be behind CloudFront.
  • • Cache Hit = found in cache. Cache Miss = retrieve from origin.
  • • index.html can be the Default Root Object.
  • • The distribution may take time to deploy.
  • • Disable a distribution before deleting it.
  • • CF and multi-region hosting solve related but different problems.

38. 🎯 Interview Questions

Q1. What is Amazon CloudFront?
An AWS CDN that distributes content through a global network to provide faster/lower-latency delivery.
Q2. Why do we need a CDN?
To deliver content from locations closer to users, reducing latency and improving performance.
Q3. What is an Edge Location?
A CloudFront location where content can be cached and served closer to users.
Q4. What is an Origin?
The original source from which CloudFront retrieves content (e.g. S3 bucket or EC2 application).
Q5. What is a Cache Hit?
Occurs when the requested content is already available at the cache and can be served from there.
Q6. What is a Cache Miss?
Occurs when the content is not available in the cache, requiring CloudFront to retrieve it from the origin.
Q7. Can CloudFront use S3 as an origin?
Yes, Amazon S3 can be configured as a CloudFront origin.
Q8. Can it work with an app on EC2?
Yes. CloudFront can be placed in front of application infra so suitable content is delivered via CDN.
Q9. Purpose of Default Root Object?
Specifies the default object to return when a user requests the root (e.g. index.html).
Q10. CF or multiple EC2 Regions?
Depends. CF is a delivery/caching layer. Multi-region distributes app infra. They can be used together.
