FOUNDATION

1. Introduction to IAM

IAM (Identity and Access Management) is one of the most important AWS services for managing authentication and authorization.

IAM helps you control:

• Who can access your AWS account
• Which AWS resources they can access
• What actions they can perform
• How much permission they should have
• How users and groups are managed
• How access is secured
Simple Definition:
AWS IAM is a service used to securely control access to AWS resources by managing identities, permissions, and authentication.
USE CASE

Organization Scenario: 50 Employees

Imagine an organization with 50 employees. Everyone cannot have complete access to everything!

PILLARS

3. IAM's Main Responsibilities

1. Identity Management 👥

Create and manage:

Users Groups Roles
2. Authentication 🔑

Verify: "Who are you?"

Examples: Username + password, MFA, other supported mechanisms.

3. Authorization 🛡️

Determine: "What are you allowed to do?"

Alex ➔ Allowed to view S3 ➔ Denied delete S3 buckets.
4. Permissions Management 📋

Define what actions users, groups, or roles can perform on AWS resources.

4. IAM Is a Global AWS Service 🌍

GLOBAL

Unlike services such as EC2 (which are tied to a specific AWS Region), IAM identities are not created separately in every region.

User "Alex" created once ➔ Active in Mumbai, Singapore, US East, Europe, etc.

Console Observation: When viewing IAM in the AWS Console, you see "Global" instead of an AWS Region selector.

5. IAM Has No Additional Charge 💰

FREE CORE

IAM itself is available without an additional charge.

⚠️ Remember: IAM being free does NOT mean the resources accessed through IAM are free!
IAM: Free EC2: Paid RDS: Paid S3: Paid

6. Root User 👑

HIGHEST ACCESS

When you initially create an AWS account, AWS creates a root user for that account.

AWS Account ➔ Root User ➔ Highest level access over everything!

The root user has unrestricted access to all resources and billing. It must be protected very carefully.

7. Why Avoid Root User Daily?

SECURITY

Using the root user for everyday operations is not recommended.

Root credentials stolen ➔ Attacker gets ultimate control ➔ Complete account compromise!
Root User:
Secure with MFA; use ONLY when required.
IAM Users/Roles:
Use for all regular AWS operations.
IDENTITIES

8. IAM Users

Individual Person / Identity

An IAM User represents an identity that can be given access to AWS resources. Each user can have different permissions:

Alex
Role: Developer
Permissions: EC2 + S3
Paul
Role: Operations
Permissions: EC2 + CloudWatch
Sarah
Role: Security
Permissions: IAM + Security Services

Each user receives permissions strictly appropriate to their job function.

COLLECTIONS

9. IAM Groups

Team Permission Bundling

An IAM Group is a collection of IAM users. Groups are useful when multiple users need similar permissions.

Without Groups (Repetitive & Painful):
• Alex ➔ Operations permissions
• Paul ➔ Operations permissions
• John ➔ Operations permissions
• Sarah ➔ Operations permissions
With IAM Groups (Clean & Scalable):
Operations Group ➔ Attach Operations Policy
➔ Add Alex, Paul, John, Sarah to Group.
All users inherit permissions automatically!

11. IAM Policies

RULES DOC

A policy is a document that defines permissions. It answers the ultimate question:

"Who can perform what action on which resource, under which conditions?"

AWS IAM policies are commonly written in JSON (JavaScript Object Notation) format.

JSON STRUCTURE

12. Basic IAM Policy Structure

Language: JSON 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "*"
    }
  ]
}
Effect: Determines whether the operation is Allow or Deny.
Action: Defines what operation is being permitted or rejected. Example: s3:GetObject.
Resource: Specifies which AWS resource the permission applies to. Example: * (wildcard = all applicable resources).

13. IAM Policy — Easy Explanation (The Instruction Sheet)

PLAIN ENGLISH

Think of a policy as a simple 4-question instruction sheet:

WHO?
Which identity?
WHAT?
Which action?
WHERE?
Which resource?
ALLOW / DENY?
What should happen?
Real Example: "Allow Alex to read objects from a specific S3 bucket."

14. Managed Policies

AWS PREBUILT

AWS provides many predefined policies for common use cases, saving admins from creating every permission from scratch:

• AdministratorAccess
• ReadOnlyAccess
• AmazonS3FullAccess
• AmazonEC2FullAccess
• CloudWatchFullAccess

15. AdministratorAccess Policy

DANGER

Provides broad access across all services. Conceptually:

Effect: Allow | Action: * | Resource: *
⚠️ Warning: The * wildcard means ALL actions on ALL resources. Never give this unnecessarily! It violates least privilege.

16. Custom IAM Policies

You can create custom policies via two approaches in the AWS Console:

1. Visual Editor: Point-and-click GUI to select Service ➔ Actions ➔ Resources ➔ Conditions.
2. JSON Editor: Directly write or modify the raw JSON policy document.

Visual Editor ↕ JSON Editor both produce the exact same policy.

GOLDEN RULE

17. Principle of Least Privilege

Definition: Give a user, application, or role only the permissions required to perform its job — nothing more.

❌ Bad Approach:
Developer ➔ AdministratorAccess (when only reading 1 S3 bucket).
✅ Better Approach:
Developer ➔ Specific S3 permissions on that specific bucket only!

TEMPORARY ACCESS

18. IAM Roles & 19. Role vs User

No Long-Term Credentials!

An IAM Role is an identity that can be assumed by trusted entities to obtain temporary permissions.

Roles are heavily used by: AWS Services, Applications, EC2 instances, Lambda functions, Users needing temporary access, Federated identities.

FeatureIAM UserIAM Role
NatureRepresents an identityProvides permissions that can be assumed
AssociationOften associated with a specific personUsed by AWS services/apps & temporary access
CredentialsCan have long-term credentials (password/keys)Designed strictly around temporary credentials
ExampleDeveloper user (Alex)EC2 instance assuming role to read S3
🧠 Memory Trick: User = Who you are | Role = What access you can assume

20. Real Example of an IAM Role

Imagine an EC2 web app that needs to read files from S3:

❌ Without a Role (Dangerous):
Hardcode Access Key + Secret Key inside the app code. (Leaking code = leaking account!)
✅ With an IAM Role (Safe):
EC2 Instance ➔ Attach IAM Role ➔ Temporary Credentials ➔ S3 Access. (Zero hardcoded keys!)

21. Federated Access (Enterprise)

Large enterprises already have their own corporate directory identity systems:

Company ➔ Active Directory / Okta IdP ➔ IAM Role ➔ AWS Access

IAM participates in identity federation, allowing companies to centralize logins without creating separate AWS users for every staff member.

SECURITY DEFENSE

22–26. Multi-Factor Authentication (MFA)

Essential Extra Layer

22. Definition: MFA adds an essential second verification layer beyond passwords.

Without MFA:
Username + Password ➔ Login (Vulnerable!)
With MFA:
Username + Password + MFA Code ➔ Login ✓
23. Why MFA is Crucial:
If a hacker steals your password, they still cannot sign in without physical possession of the MFA device!
24. Common MFA Methods:
• Authenticator Apps (Google Auth, Authy)
• Hardware Security Keys (YubiKey)
• Other supported token devices
25. MFA Example (TOTP):
Phone app displays rotating 6-digit code (e.g. 123456). Code changes every 30 seconds!
26. Protect the Root User with MFA: One of the most important AWS security mandates. Enable MFA on root immediately!

CRITICAL WARNING

37–38. Protect Access Keys & Never Commit to Git!

Bot Scanners Alert

37. Access keys are sensitive credentials. Never send them in chats, upload to GitHub, commit to source code, store in public repos, put in screenshots, or share in documents.

Hardcode Keys in Code ➔ Git Commit ➔ Push to GitHub ➔ Attacker Scans Repo ➔ Full Account Compromised! 💸
38. Modern Secure Approach: Use IAM Roles, AWS Secrets Manager, environment variables, or temporary STS credentials. Never bake static keys into files!

39–40. Access Key Creation & Config

39. Critical Rule: The Secret Access Key is shown only once at creation. Download/save it securely immediately!

8 RULES

49. IAM Security Best Practices

Industry Gold Standards
1. Avoid Root Daily: Use root only for initial setup.
2. Enable MFA: Mandate MFA on Root & privileged users.
3. Use Groups: Assign permissions to teams, not users.
4. Least Privilege: Grant minimum necessary rights.
5. Protect Keys: Never commit access keys to code/git.
6. Audit Regularly: Run Credential Reports periodically.
7. Clean Unused: Disable/delete inactive credentials.
8. Prefer Roles: Use IAM Roles over hardcoded keys.

51 & 54. Complete Access Model

Identity (User/Role) ➔ Policy ➔ Action ➔ Resource ➔ Evaluation
54. IAM Evaluation Rule:
By default, all requests are DENIED. An explicit ALLOW grants access. However, an explicit DENY always overrides any ALLOW!

52–53. Practical Example: Adding & Removing Developers

WORKFLOW
Step 1: Create Users (Alex, Paul)
Step 2: Create Group (Developers)
Step 3: Attach S3 Policy to Group
Step 4: Add Users to Group

53. What happens when Alex is removed from Developers? He instantly loses all S3 permissions inherited through that group! No manual revocation needed per service.

61. Top 20 Interview Questions & Answers

Q1. What is AWS IAM?

Ans: A service used to securely manage identities and control access to AWS resources through authentication and authorization.

Q2. Is IAM regional or global?

Ans: IAM is a global service. Identities and policies are not created separately for each AWS Region.

Q3. Is IAM free?

Ans: Yes, IAM is offered at no additional charge. However, resources managed via IAM (EC2, S3) incur standard charges.

Q4. What is the AWS root user?

Ans: The original identity created with the AWS account. Has complete access; must be locked with MFA and avoided for daily tasks.

Q5. What is an IAM user?

Ans: An identity representing a person or application that can be granted granular permissions to access AWS resources.

Q6. What is an IAM group?

Ans: A collection of IAM users. Permissions assigned to the group are automatically inherited by all its members.

Q7. Why use IAM groups?

Ans: To simplify permission administration by assigning common policies centrally rather than individually.

Q8. What is an IAM policy?

Ans: A JSON document that formally defines permissions (Effect, Action, Resource, Condition) for identities.

Q9. What is the Principle of Least Privilege?

Ans: Granting only the minimum required permissions necessary for an identity to perform its job — nothing more.

Q10. What is an IAM role?

Ans: An identity with permissions that can be assumed by trusted entities (services, users, apps) using temporary credentials.

Q11. What is MFA?

Ans: Multi-Factor Authentication. Adds an additional verification factor (e.g. 6-digit TOTP code) beyond the password.

Q12. Why enable MFA for root?

Ans: Because the root user has ultimate power. MFA ensures account safety even if the root password is compromised.

Q13. Difference: Authentication vs Authorization?

Ans: Authentication = "Who are you?" (login). Authorization = "What are you allowed to do?" (permissions).

Q14. What are access keys used for?

Ans: Credentials (Key ID + Secret Key) used for programmatic access to AWS via CLI, SDKs, and APIs.

Q15. What is AWS CLI?

Ans: A unified command-line tool to manage and interact with AWS services using terminal commands and scripts.

Q16. Why is AWS CLI useful?

Ans: Enables task automation, repetitive batch operations, scripting, DevOps pipelines, and headless administration.

Q17. What is AWS SDK?

Ans: Software Development Kits enabling software applications (Python, Java, Node.js) to call AWS APIs programmatically.

Q18. 3 Main ways to access AWS?

Ans: 1. AWS Console (Click), 2. AWS CLI (Command), 3. AWS SDK/APIs (Code).

Q19. What is a Credential Report?

Ans: An auditing CSV report showing password status, access key age, and MFA adoption across all account users.

Q20. Why never commit keys to GitHub?

Ans: Automated bots scan public repos within seconds, hijacking credentials to run malicious crypto miners or steal data.

💡 8 Bonus Study Tips for AWS IAM (Plain English!)

Simple methods to remember IAM concepts forever and ace cloud security viva questions.

1. Mind Maps 🗺️

In simple terms: Put "IAM" in the center circle. Draw 4 branches: Identities (Root, Users, Groups, Roles), Policies (JSON, Managed, Custom), Access (Console, CLI, SDK), and Security (MFA, Least Privilege, Credential Report). It stops topic mix-up instantly!

2. Flow Charts ➔

In simple terms: Draw this evaluation chain: Request ➔ Authenticate ➔ Any Explicit Deny? (Yes ➔ Denied) ➔ Any Explicit Allow? (Yes ➔ Allowed) ➔ Otherwise Denied by Default.

3. Formula / Rule Box 📦

In simple terms: Memorize the 3 core identities: User = Person (Long-term), Group = Team (Policy container), and Role = Coat you put on (Temporary STS credentials).

4. Revision Section ⏱️

In simple terms: Before every lab, do a 30-second rapid check: "Am I on Root? (Stop!). Is MFA on? Have I attached a Role instead of typing Secret Keys?"

5. Highlighted Keywords 🖍️

In simple terms: Examiners listen for trigger words: "Global Service", "Least Privilege", "Temporary Credentials", "Explicit Deny", and "Credential Report".

6. Colour Coding 🎨

In simple terms: Use Red pen for hazards (Root login, Git commits, AdminAccess), Blue pen for policy structure and groups, and Yellow highlighter for CLI commands like aws configure.

7. Important Questions 🎯

In simple terms: Practice the Big 3 viva questions out loud: 1. What is the difference between an IAM User and an IAM Role?, 2. Authentication vs Authorization?, and 3. What is Least Privilege?

8. Quick Summary 📝

In simple terms: Conclude any IAM interview answer with: "In summary, IAM is a free, global service that secures AWS by authenticating identities and enforcing least privilege policies across users, groups, and temporary roles."
