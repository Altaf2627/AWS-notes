AWS ECS (Elastic Container Service)

1. What is Amazon ECS?

Amazon ECS (Elastic Container Service) is a cloud-based container management service provided by AWS.

It allows you to run and manage containerized applications, especially Docker containers, on AWS infrastructure.

Simple Definition Amazon ECS is a managed AWS service used to deploy, run, manage, and scale container-based applications.

ECS can work with: Docker containers, Container images stored in registries such as Amazon ECR, and other supported/private container registries.

2. Why Use Amazon ECS?

Suppose you have developed an application and:

  • Created the application
  • Containerized it using Docker
  • Built a Docker image
  • Uploaded the image to a container registry
  • Now want to deploy it

Without ECS, manual work:

  • Set up servers & Install Docker
  • Configure the application
  • Run & Monitor containers
  • Restart failed containers
  • Handle scaling & Manage instances

ECS simplifies this process.

You provide ECS with information such as: Which container image to use, How much CPU/memory is required, Which ports to expose, Environment variables, and How many copies of the application should run.

ECS then manages much of the container deployment and operation for you.

3. Basic ECS Architecture

The three most important ECS terms are: Cluster, Service, Task.

And another important concept is: Task Definition.

ECS │ └── Cluster │ ├── Service │ ├── Task │ ├── Task │ └── Task │ └── Task Definition

4. ECS Cluster

What is a Cluster? An ECS Cluster is a logical grouping that contains the resources and infrastructure used to run your ECS workloads.

Easy way to remember:

Cluster = Place/group where your ECS workloads run.

My Cluster │ ├── Service │ ├── Task 1 │ └── Task 2 │ └── Other Services

A cluster can contain multiple services and tasks.

5. ECS Service

An ECS Service is responsible for maintaining and managing the desired number of running tasks.

It helps with: Maintaining the desired number of tasks, Scaling, Deployments, Replacing failed tasks, Integration with load balancing.

Example

Suppose you want 2 copies of your app running. You configure: Desired Tasks = 2

Before:

Task 1 → Running Task 2 → Running

Task 2 fails...

After:

Task 1 → Running Task 2 → New replacement task

The ECS service can maintain the desired number of tasks.

Remember Service = Manages how many tasks should be running and how they are deployed/scaled.

6. ECS Task

A Task represents a running instance of your containerized application.

Task └── Container └── Nginx

If you run two copies:

  • Task 1 → Nginx Container
  • Task 2 → Nginx Container

Therefore: Task = A running workload/container execution in ECS.

7. Task Definition

A Task Definition is a blueprint/configuration that tells ECS how your container should run.

It can specify things such as:

  • Container image & name
  • CPU & Memory
  • Port mappings
  • Environment variables
  • Logging configuration
  • Storage & Health checks

Docker comparison

With Docker, you might run:

docker run -p 80:80 -e ENV=production nginx

In ECS, many of these configuration details are defined in the Task Definition.

Easy memory trick Task Definition = Blueprint | Task = Running instance created from that blueprint

8. Cluster → Service → Task → Container

This is one of the most important concepts.

ECS │ └── Cluster │ └── Service │ ├── Task 1 │ └── Container │ └── Task 2 └── Container

The Task Definition tells ECS how those tasks should be configured.

9. ECS Infrastructure Options

When creating an ECS cluster, you need to decide where/how your containers will run. The transcript demonstrates two important options:

1. AWS Fargate

Fargate is a serverless compute option for containers. You don't have to manually manage the underlying EC2 servers.

Your Application ↓ Container ↓ ECS + Fargate ↓ AWS-managed infra

2. EC2

With the EC2 option, you use EC2 instances as the compute infrastructure for your containers.

You have more control over the underlying instances, but also more infrastructure management responsibilities.

10. Fargate vs EC2

Feature Fargate EC2
Server management AWS manages underlying infra You manage EC2 instances
Infrastructure control Lower Higher
Operational effort Lower Higher
Good for Simpler container deployments Workloads requiring more instance-level control
Scaling ECS/Fargate handles capacity You manage instance capacity + ECS
Serverless experience Yes No
Simple rule Want less infrastructure management → Fargate | Want more control over servers → EC2

Task Definition Details (15 - 20)

15. Port Mapping

Nginx is a web server, so HTTP traffic needs to reach the container. Container Port: 80

Internet↓HTTP :80↓ECS Task↓Nginx :80

16. CPU and Memory

You can configure the resources allocated. Resource limits help prevent one workload from consuming unlimited resources, control costs, and improve resource planning.

17. Env Variables & 18. Logging

Env Vars: Allows configuration to be separated from app code. (e.g., ENV=prod).

Logging: Enable container logging (commonly to CloudWatch Logs) for troubleshooting.

19. Health Checks & 20. Create

Health Checks: Determine if app is functioning. Unhealthy tasks can be replaced.

20. Create: After configuring Image, Port, CPU, Memory, Env vars, Logs, Health checks, you create the Task Definition.

Creating an ECS Service (21 - 24)

Cluster→Create Service→Select Task Definition→Name: my-service

22. Desired Tasks & 23. Why?

Desired Tasks = 2

Running multiple tasks improves availability. If Task 1 fails, the service attempts to start a replacement to maintain the desired count of 2.

24. Networking Config

Configure VPC, Subnets, SG, Public IP. For HTTP app, allow HTTP Port 80. Best Practice: Don't blindly allow 0.0.0.0/0 for every port. Only expose what's needed.

Running and Updating (25 - 29)

25. Public IP: If task needs internet access, enable Public IP. Internet → Public IP → ECS Task

26. Auto Start: Service automatically starts tasks to meet desired count. PENDING → RUNNING

27. Checking: Service → Tasks tab shows status, IP, logs, etc.

28. Accessing & 29. Updating

If HTTP 80 is allowed, http://<PUBLIC-IP> shows the Nginx page.

29. Updating: You can change service config. Update Desired Count 2 → 1, and ECS will reduce running tasks to match.

30. Scaling  |  31. ECS + Load Balancer

ECS services can be configured for scaling according to workload requirements.

Internet ↓ Load Balancer ↓ ┌─────────┴─────────┐ ↓ ↓ Task 1 Task 2 ↓ ↓ Container Container

Why a Load Balancer?

If many users access your application, the load balancer can distribute requests across healthy tasks.

This improves: Availability, Scalability, Traffic distribution.

32. ECS Logging

Container→ECS→CloudWatch Logs

Logs are useful for debugging, error analysis, monitoring, and troubleshooting.

39. Cleanup  |  ⭐ Best Practices

39. Cleanup

Don't create resources and forget them. Flow:

Delete/scale down Service Stop running Tasks Deregister Task Defs Delete Cluster
  • 1. Prefer Fargate when you don't need server-level control.
  • 2. Least-privilege IAM permissions.
  • 3. Restrict Ports: Only allow required traffic via SGs.
  • 4. Use CloudWatch for proper logging.
  • 5. Multiple tasks for important apps (HA).
  • 6. Load Balancer for production web apps.

🧠 Quick Revision & 🎯 Interview Questions

Quick ECS summary

  • Managed container orchestration service.
  • Cluster groups workloads.
  • Service manages running tasks & capacity.
  • Task = running workload.
  • Task Definition = blueprint.
  • Fargate = Serverless containers.
  • EC2 = More server control.
Q1. Fargate vs EC2?
Fargate: Serverless, AWS manages infra. EC2: You manage instances.
Q2. Task vs Task Definition?
Task Definition is the blueprint. Task is the running instance based on it.
Q3. Why run multiple tasks?
To improve availability and handle more traffic. Service maintains desired count.
⭐ The Easiest Formula to Remember

ECS → Cluster → Service → Tasks → Containers

Task Definition = Instructions/Blueprint for those Tasks.
