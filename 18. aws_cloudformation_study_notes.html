AWS CloudFormation — Structured English Notes

1. What is AWS CloudFormation?

AWS CloudFormation is an Infrastructure as Code (IaC) service provided by AWS.

Infrastructure as Code (IaC)

IaC means: Creating and managing cloud infrastructure using code instead of doing everything manually through the AWS Console.

For example, instead of manually creating an EC2 instance by selecting:

  • AMI
  • Instance type
  • Storage
  • Security Group
  • Other settings

you can define all of these in a CloudFormation template. CloudFormation then creates the required resources automatically.

2. Manual Infrastructure vs CloudFormation

Traditional/manual approach

AWS Console↓Create EC2↓Select AMI↓Select Instance Type↓Configure Storage↓Configure Security Group↓Review↓Create Instance

This involves a lot of manual work.

CloudFormation approach

CloudFormation Template↓Create Stack↓CloudFormation reads template↓AWS Resources↓Resources created

The main benefit is automation and repeatability.

3. CloudFormation Template

A template is a file that describes the infrastructure you want CloudFormation to create.

CloudFormation templates can be written in: YAML or JSON

Example:

Resources: MyInstance: Type: AWS::EC2::Instance Properties: InstanceType: t3.micro ImageId: ami-xxxxxxxx Tags: - Key: Name Value: MySimpleInstance

This template says: "Create an EC2 instance with this AMI, this instance type, and this name."

4. Declarative Approach

CloudFormation follows a declarative approach.

What does declarative mean?

You specify: WHAT you want

rather than explaining every individual step of: HOW to create it.

For example, you just declare:

Type: AWS::EC2::Instance Properties: InstanceType: t3.micro ImageId: ami-xxxxxxxx

You don't manually write: Open EC2 → Click Launch Instance → Select AMI → Configure settings → Launch. Instead, you declare the desired infrastructure state.

5. Important CloudFormation Terms

A. Template

The file containing your infrastructure definition. Formats: YAML or JSON

B. Stack

A Stack is a collection of AWS resources created and managed together from a CloudFormation template.

CloudFormation Stack │ ├── EC2 Instance ├── Security Group └── Elastic IP

Instead of managing every resource separately, you can manage them as one logical unit.

C. Resources

Resources are the AWS services/components defined in the template. Examples: EC2, S3, VPC, Security Group, Elastic IP, RDS, Lambda, IAM resources, Load Balancer.

6. Creating a Stack

Create Stack→Choose Template→Upload Template→Specify Stack Name→Configure Options→Review→Create Stack

You can use: Existing templates, Sample templates, Templates stored locally, Templates stored in Amazon S3, or Infrastructure Composer.

7. AWS Infrastructure Composer

CloudFormation provides Infrastructure Composer for visualizing infrastructure. Instead of seeing only code, you can visualize resources and their relationships.

Security Group │ ↓ EC2 Instance ↑ │ Elastic IP

Benefits:

  • Visual understanding of architecture
  • See resource relationships
  • Review infrastructure
  • Edit & Validate templates

This is particularly useful when a template contains many interconnected resources.

8. CloudFormation Stack Lifecycle

A basic stack can go through three important operations:

Create

Template→Create Stack→Resources Created

Update

Existing Stack→Modify Template→Preview Changes→Update Stack

Delete

Delete Stack→CloudFormation Deletes Resources
Create → Update → Delete are fundamental CloudFormation operations.

9. Updating a Stack  |  10. Change Sets

Suppose the original template contains: InstanceType: t3.micro. Later you change it to: InstanceType: t2.micro. You can update the existing stack instead of manually modifying the infrastructure.

10. Change Sets

A Change Set allows you to preview proposed infrastructure changes before applying them.

Current Template↓Modified Template↓Change Set↓Review Changes↓Execute Update
Important Note on Changes

The change preview can indicate whether a resource will be: Modified, Replaced, Deleted, or Created.

A resource replacement can mean the existing resource is removed and a new resource is created.

Therefore, always review changes carefully before executing an update.

11. Example: Simple Name Update

Suppose the instance initially has: MySimpleInstance. You change it to: MyDemoInstance.

CloudFormation can identify the change and update the stack. If the change does not require replacing the underlying resource, the existing resource can remain while its applicable property is updated.

12. Rollback and Failure Handling

One of CloudFormation's important capabilities is rollback. Suppose you attempt an invalid update: t3.micro → Invalid configuration → Update fails.

CloudFormation can roll back the stack to the previous successful state, depending on the operation and configuration.

Previous State→Update→ERROR→ROLLBACK→Previous Successful State

Example from the transcript

An update attempted to change the instance type to t2.micro, but the configuration was not valid in that environment/region. The update failed and CloudFormation rolled the stack back. The EC2 instance therefore remained in its previous working state.

13. Why Rollback is Important

Without proper state management, a failed infrastructure update could leave resources partially modified. CloudFormation helps maintain the intended stack state and provides mechanisms for handling failed operations.

Key Idea If an update fails, CloudFormation can attempt to restore the previous successful state.

14. Multiple Resources  |  15. Resource References

One of the biggest advantages of CloudFormation is that one template can create multiple related resources.

CloudFormation Stack │ ├──────── EC2 Instance │ ├──────── Security Group │ └──────── Elastic IP

15. Resource References

Resources can reference one another. The EC2 instance can reference the Security Group created in the same template. Similarly, the Elastic IP can reference the EC2 instance. This allows CloudFormation to understand relationships between resources.

16. Example: Web Server Stack

A more advanced template can automatically create a complete basic web server environment.

Internet │ ↓ Elastic IP │ ↓ EC2 Instance │ Security Group │ ↓ Web Server │ ↓ HTML Web Page

17. Security Group in Template

For a web server, the Security Group can allow HTTP traffic (Port 80) from the Internet. Note: In production, security rules should be restricted appropriately rather than unnecessarily exposing services to the entire internet.

18. Elastic IP

An Elastic IP is a static public IPv4 address. Without a persistent public address, the public IPv4 address associated with an instance can change in certain lifecycle situations. Using an Elastic IP provides a stable address for the application.

19. CloudFormation & Automation  |  20. Major Use Cases

CloudFormation becomes especially useful when infrastructure needs to be created repeatedly.

Create Template Once→Reuse Template→Create Infrastructure→Reuse Again→Create Infrastructure

20. Major Use Cases

1. Consistency: Same Template → Same Configuration → Consistent Infrastructure. Reduces manual configuration differences.

2. Automation: Can be incorporated into automated workflows (e.g., Scheduled Job → AWS CLI → CloudFormation → Create Stack).

3. Repeatable Environments: You can create similar environments for Development, Testing, Staging, and Production using the same base infrastructure definition with different parameters.

22. Stack Deletion  |  23. Cost Management Benefit

Instead of manually deleting each resource (EC2, SG, EIP), you can delete the stack: Delete Stack → CloudFormation → Delete Stack Resources. This is especially useful for temporary environments.

⚠️ Important Always understand a resource's deletion behavior before deleting a production stack. Some resources may have retention policies.

23. Cost Management

CloudFormation itself does not generally charge simply for the existence of a template or stack. However, the AWS resources created by CloudFormation (EC2, RDS, NAT, etc.) can incur charges. Deleting unused stacks helps prevent unnecessary resource charges.

24. StackSets

A normal CloudFormation stack is generally deployed in a particular AWS account and region. For larger organizations, CloudFormation StackSets allow you to deploy CloudFormation stacks across Multiple AWS accounts and Multiple AWS Regions.

StackSet │ ┌─────────┼─────────┐ ↓ ↓ ↓ Account A Account B Account C │ │ │ Region 1 Region 1 Region 2

Use case: Organizations can use StackSets to deploy standardized infrastructure across many accounts and regions.

25. CloudFormation and AWS CLI

CloudFormation can also be operated through the AWS CLI.

Local Template→AWS CLI→CloudFormation→Create Stack
aws cloudformation create-stack \ --stack-name demo-stack \ --template-body file://template.yaml

The AWS CLI must be configured with appropriate credentials and region settings.

26. Documentation  |  27. Resource Types

27. Resource Type

A resource declaration typically contains: Type: AWS::EC2::Instance. This tells CloudFormation which AWS resource should be created.

Examples: AWS::S3::Bucket, AWS::RDS::DBInstance, AWS::Lambda::Function

28. Common CloudFormation Use Cases

  • EC2: EC2 Instance + Security Group + Elastic IP
  • S3: S3 Bucket
  • Networking: VPC, Subnets, Route Tables, Internet Gateway, Security Components
  • Database: RDS Database + Backup Configuration
  • Serverless: Lambda + API Gateway
  • Web App: Load Balancer → Auto Scaling → EC2 Instances

29. Drift Detection

Drift Detection identifies changes made to resources outside CloudFormation.

Example: Your template says: EC2 configuration = A. But someone manually changes the resource through the AWS Console to configuration = B. Now there is a difference between Template State vs Actual Resource State. This difference is called drift.

CloudFormation Template │ │ expected state ↓ Resource ↑ │ actual state │ Manual Console Change
