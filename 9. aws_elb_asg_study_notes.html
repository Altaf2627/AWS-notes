AWS Elastic Load Balancing (ELB) & Auto Scaling Groups (ASG)

1. Overview

This section covers two important AWS concepts:

  • Elastic Load Balancing (ELB)
  • Auto Scaling Groups (ASG)

Before understanding ELB and ASG, three concepts are important:

  • Scalability
  • High Availability
  • Elasticity

2. Scalability

Definition

Scalability is the ability to increase or decrease computing resources to handle changes in workload or traffic.

Example

Suppose a website is running on one EC2 instance. Suddenly, traffic increases significantly.

Normal Traffic
↓
1 EC2
↓
Website

When traffic becomes high, the existing resources may not be sufficient. You can scale the resources to handle the additional load. AWS provides different ways to scale.

3. Types of Scalability

There are two major types:

  • Vertical Scaling
  • Horizontal Scaling

4. Vertical Scaling — Scaling Up

Vertical scaling means increasing the capacity of an existing EC2 instance.

t2.micro → m5.large

You increase resources such as: CPU, RAM, Computing power.

Example

Suppose your website is running on t2.micro and traffic increases. You can move to a more powerful instance type such as m5.large. The same instance now has greater computing capacity.

Memory Trick

Vertical = Make the existing machine bigger.

Small EC2
↓
Bigger EC2

5. Horizontal Scaling — Scaling Out

Horizontal scaling means adding more EC2 instances. Instead of making one server bigger, you add multiple servers.

Before:

EC2 ↓ Website

After:

EC2 #1 ↓ EC2 #2 ↓ EC2 #3 ↓ EC2 #4

All instances can work together to handle incoming traffic.

Memory Trick Horizontal = Add more machines.

6. Vertical vs Horizontal Scaling

Feature Vertical Scaling Horizontal Scaling
Also called Scaling Up Scaling Out
Method Increase capacity of one instance Add more instances
Example t2.micro → m5.large 1 EC2 → 3 EC2
Main resource CPU/RAM/compute power Number of servers
Multiple servers No Yes
Easy Memory Trick

Scale Up = Bigger Server

Scale Out = More Servers

7. High Availability (HA)

Definition

High Availability means keeping an application/service available with minimal downtime. The goal is: Users should be able to access the application even if a resource or infrastructure component fails.

Example

Suppose your website is running on one EC2 instance. If that EC2 instance fails:

EC2
↓
Website
↓
FAILURE
↓
Website Down

This creates a single point of failure.

8. High Availability Using Multiple Availability Zones

To improve availability, you can run resources across multiple Availability Zones (AZs).

Availability Zone A
↓
EC2 #1
Availability Zone B
↓
EC2 #2

If one Availability Zone experiences a problem, the other can continue serving users.

Key Idea High Availability = Keep the application running despite failures.

9. Scalability vs High Availability

Scalability High Availability
Handles increasing/decreasing workload Handles failures and reduces downtime
Focuses on capacity Focuses on availability
Adds or increases resources Uses redundancy
Example: Add EC2 instances Example: Run EC2 across AZs
Simple Memory Trick

Scalability = Can I handle more traffic?

High Availability = Can I stay online if something fails?

10. Elasticity

Definition

Elasticity is the ability to automatically adjust resources according to demand.

Traffic increases
↓
Add resources automatically
↓
Traffic decreases
↓
Remove unnecessary resources

Example

Suppose normally you need: 2 EC2 instances

During peak traffic: 2 → 5 EC2 instances

When traffic becomes normal: 5 → 2 EC2 instances

This automatic adjustment is the key idea behind elasticity.

11. Elasticity vs Scalability

A useful distinction from this section:

  • Scalability → Ability to increase/decrease capacity.
  • Elasticity → Automatic adjustment of capacity based on demand.

12. What is Elastic Load Balancing?

ELB (Elastic Load Balancing) distributes incoming traffic across multiple resources such as EC2 instances.

Instead of users directly accessing individual EC2 instances, users can access the Load Balancer.

Users ↓ Load Balancer ↓ ┌───────┬───────┬───────┐ EC2 #1 EC2 #2 EC2 #3

13. Why Do We Need a Load Balancer?

Suppose you have three EC2 instances running the same website. The question becomes: Which EC2 instance should receive each request?

The Load Balancer handles this responsibility. It accepts incoming requests and distributes them among the available instances.

User 1 ──┐ User 2 ──┼──→ Load Balancer User 3 ──┘ │ ┌──────┼──────┐ ↓ ↓ ↓ EC2-1 EC2-2 EC2-3

14. Benefits of Load Balancing

1. Traffic Distribution: Traffic is distributed across multiple EC2 instances.

2. Improved Availability: If one instance fails, traffic can continue to healthy instances.

3. Scalability: More instances can be added behind the Load Balancer.

4. Single Point of Access: Users access the Load Balancer instead of exposing individual EC2 instances directly.

15. Load Balancer + Multiple Availability Zones

For better availability, instances can be distributed across multiple AZs.

Load Balancer │ ┌───────────┼───────────┐ ↓ ↓ ↓ AZ-A AZ-B AZ-C EC2 EC2 EC2

This provides two major benefits: Traffic distribution & Higher availability/fault tolerance.

16. ELB Types

The section introduces these load balancer types:

17. Application Load Balancer (ALB)

Primarily designed for application-level traffic: HTTP, HTTPS

Works at: OSI Layer 7 — Application Layer

Common Use Case: Websites and web applications.

User
↓
HTTP/HTTPS
↓
ALB
↓
EC2

18. Network Load Balancer (NLB)

Designed for high-performance, low-latency network traffic.

Works at: OSI Layer 4 — Transport Layer (TCP, UDP, TLS)

Common Use Cases: High-performance apps, real-time apps, gaming, financial apps.

19. Gateway Load Balancer (GWLB)

Designed to deploy and manage third-party virtual appliances. Examples include: Firewalls, Monitoring solutions, Security appliances.

Client
↓
GWLB
↓
Third-Party Appliance
↓
Server

A useful testing technique is to display the hostname of the EC2 instance on the webpage.

Welcome to Web Server

Now, when the Load Balancer distributes requests, you can identify which server responded.

Components of Load Balancer Setup (25 - 29)

25. Availability Zones

For better High Availability, place instances in different Availability Zones: AZ-A → EC2 #1, AZ-B → EC2 #2. This improves fault tolerance.

26. Security Group

The Load Balancer needs an appropriate Security Group. For an HTTP website: HTTP | Port 80 | Source: Anywhere.

27 & 28. Target Group

A Target Group contains the targets to which the Load Balancer forwards requests.

Config: Target type → EC2 instances | Protocol → HTTP | Port → 80 | Health check → HTTP

29. Listener

The Load Balancer listens for incoming requests on a specified port (e.g., HTTP : 80).

30. Complete Request Flow

User │ ↓ Load Balancer │ HTTP : 80 Listener │ ↓ Target Group / \ / \ ↓ ↓ EC2 #1 EC2 #2 │ │ ↓ ↓ Website Website

31. Health Checks & Fault Tolerance

A Load Balancer checks whether registered targets are healthy. If an instance stops responding (Unhealthy), the Load Balancer can stop sending traffic to it.

Key Benefit Traffic is sent to healthy targets.

33. Testing Distribution: Refreshing the webpage can show different hostnames (Server 1, Server 2), proving load distribution.

34 & 35. When an Instance Stops

If EC2 #2 stops, ELB detects it as Unhealthy and routes all traffic to EC2 #1. This demonstrates fault tolerance.

Important: Health checks take time. Do not expect the health status to change instantly when an instance stops or starts.

36. Auto Scaling Group (ASG)

ASG = Auto Scaling Group

An Auto Scaling Group automatically manages the number of EC2 instances according to defined requirements and policies. It can: Add EC2 instances, Remove EC2 instances, Replace unhealthy instances, Maintain a desired number of instances.

37. Why Do We Need ASG?

Manually managing EC2 instances during high/low traffic is inefficient. ASG automates the process.

38. ASG and Elasticity

ASG provides elasticity. High Traffic → 4 EC2. Low Traffic → 2 EC2. Automatic adjustment.

39. Main Functions of ASG

  • 1. Automatic Scaling: Increase or decrease instances.
  • 2. Health Management: Replace unhealthy instances.
  • 3. Maintain Desired Capacity: Keep a specific number running.
  • 4. Scaling Policies: Rules based on CPU or request count.
  • 5. Scheduled Scaling: Scale at specific predictable times.
  • 6. Multi-AZ Deployment: Distribute across AZs for HA.
  • 7. Load Balancer Integration: Works with ELB to distribute traffic to the scaled instances.

40. Very Important — ELB vs ASG

A common confusion is: "Does ASG distribute traffic?" No.

ELB

Handles: Traffic distribution

ASG

Handles: Number of EC2 instances

41. ELB + ASG Together

Users │ ↓ Load Balancer │ ↓ Target Group │ ┌───────────┼───────────┐ ↓ ↓ ↓ EC2 #1 EC2 #2 EC2 #3 ↑ ↑ ↑ └──────── Auto Scaling ────────┘

Together they provide: Scalability, Elasticity, High Availability, Fault tolerance.

42. Desired, Minimum and Maximum Capacity

Minimum Capacity: Minimum number of instances (e.g., Min = 1)

Desired Capacity: Normal/target number of instances (e.g., Desired = 2)

Maximum Capacity: Maximum instances ASG can create (e.g., Max = 3)

Normal condition: 2 instances

High demand: 2 → 3 instances

Low demand: 2 → 1 instance

43 & 44. ASG + Launch Templates & AMIs

ASG needs a way to know how new EC2 instances should be launched. This is why a Launch Template is important.

AMI
↓
Launch Template
↓
ASG
↓
Creates EC2

You need an AMI so you don't launch empty instances. The AMI contains the web server, application, and configuration.

45. ASG Creation Flow

1. Create AMI → 2. Create/Use Launch Template → 3. Create Auto Scaling Group ↓ 4. Select AZs/Subnets → 5. Attach Load Balancer → 6. Configure Health Checks ↓ 7. Set Minimum/Desired/Maximum → 8. Configure Scaling Policy → 9. Create ASG

48. Multiple AZs

ASG can distribute instances across AZ-A, AZ-B, AZ-C to ensure if one zone fails, others continue.

49 & 50. LB & Health

ASG uses the ELB Target Group. ASG can use LB health checks to detect and replace unhealthy instances automatically.

Scaling Policies (51 - 54)

  • CPU-Based Scaling: e.g., Target Average CPU Utilization = 50%. ASG attempts to maintain this target.
  • Request-Based Scaling: More Requests → Higher Load → Add Instances.
  • Scheduled Scaling: Useful when traffic patterns are known (e.g., 6 PM → Increase, 12 AM → Reduce).

55. Maintaining Desired Capacity

If Desired = 2, and one instance is manually terminated, ASG notices the shortage and launches a replacement. ASG tries to maintain the configured capacity. (Sec 56: You can view Activity History to see what happened and why).

57. Practical Example — Complete Architecture

Traffic Flow:

User → Load Balancer → Target Group → Healthy EC2

Scaling Flow:

High Traffic → Scaling Policy → ASG → Launch new EC2 → Target Group → Load Balancer

59 & 60. Cleanup After Practical Work

Important Rule: Delete the ASG First!

If you manually terminate instances while the ASG is active, ASG sees capacity below desired and will just launch replacements. Delete ASG → Delete LB → Terminate EC2.

61. Most Important Differences

Scalability vs HA Scalability = Handle workload. HA = Minimize downtime.
Vertical vs Horizontal Vertical = Bigger instance. Horizontal = More instances.
ELB vs ASG ELB = Distributes traffic. ASG = Manages EC2 capacity.
AMI vs Launch Template AMI = Machine image. Launch Template = EC2 launch config.
AMI → What should the EC2 contain? Launch Template → How should EC2 be launched? ASG → How many EC2 instances should exist? ELB → Where should user traffic go?
